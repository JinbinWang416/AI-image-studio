## 一、⛔ 必须先确认的 4 个架构分叉点

这四点决定数据模型，**定错了后期返工代价极大**，所以先问再动手。

### Q1. 「多个人」是什么关系？

| 选项 | 含义 | 架构差异 |
|------|------|---------|
| **A** | 同一家公司内的同事（老板 / 设计 / 客服） | 单组织 + 角色权限即可 |
| **B** | 多个**不同客户**（每个客户有自己的门店） | **必须多租户 + 数据完全隔离** |
| **C** | 混合（内部员工 + 外部客户） | 多租户 + 内部跨租户角色 |

> 你说「会有真实客户数据」，听起来倾向 B 或 C —— 但需要你确认。

### Q2. 批次数据是否按人隔离？

- **A**：所有人共享全部批次（内部协作场景）
- **B**：每人/每组织只能看自己的批次（客户场景）
- **C**：可配置（创建时选「私有 / 组织内共享 / 公开」）

### Q3. 是否需要「组织」这一层？

- **A**：不需要，用户直接挂权限
- **B**：需要（公司 → 部门 → 用户）

### Q4. 现有数据如何归属？

现在 `output/` 里有 **4 个批次 + 46 张 AI 背景 + 基准样本**。
账号体系上线后，这些历史数据归谁？

- **A**：归给首个管理员账号
- **B**：标记为「系统公共资产」（所有登录用户可见）
- **C**：按门店/批次手工分配

## 二、分阶段实施规划

> 原则（文档 §2）：先检查 → 再方案 → 后实施；渐进迁移；提供回滚

### 阶段 0 · 安全基线（1~2 天）

**必须在开放 `0.0.0.0` 之前完成**，否则等于把工具裸奔在网络上。

| # | 项 | 说明 | 依据 |
|---|----|------|------|
| 0-1 | **修 SSRF** | `base_url` 白名单校验：仅 `https://`、拒绝内网段与裸 IP、不跟随重定向 | §11 |
| 0-2 | **强制认证护栏** | `--host` 非本机时，**若无账号体系则拒绝启动**（而不是警告） | §4「默认拒绝」 |
| 0-3 | 安全响应头 | `nosniff` / `X-Frame-Options: DENY` / `Referrer-Policy` | §11 |
| 0-4 | 依赖固定版本 | `requirements.txt` 改 `==` | §12 |
| 0-5 | 错误响应收敛 | 确认所有出口不泄露堆栈/路径 | §11 |

**交付物**：现状报告 + 修复证据 + 测试结果

---

### 阶段 1 · 账号与认证（3~5 天）

| # | 项 | 要点 | 依据 |
|---|----|------|------|
| 1-1 | 用户数据模型 | 内部稳定 ID（不可变）+ 登录名 + 显示名 + 状态（待激活/正常/冻结/停用） | §3.1~3.5 |
| 1-2 | 登录名规范化 | 大小写、空格、全半角、Unicode 规范化，防同形账号 | §3.3 |
| 1-3 | 密码存储 | **argon2id** 或 bcrypt（成熟库，不自行设计） | §3.7 |
| 1-4 | 会话管理 | 空闲超时 + 绝对有效期；登录/提权后**轮换会话标识**；安全 Cookie 属性 | §3.10~3.11 |
| 1-5 | 登录防护 | 限流 + 防枚举（错误信息不区分「用户名不存在」与「密码错误」） | §3.8 |
| 1-6 | 会话撤销 | 停用账号**立即**阻止新请求并撤销已有会话；用户可查看/撤销自己的设备 | §3.6 / §3.12 |
| 1-7 | 权限变更即时生效 | 改密码/角色/状态后，旧会话立刻失效 | §3.13 |
| 1-8 | 管理员 MFA | TOTP（可用 `pyotp`），敏感操作二次认证 | §3.9 |

**为什么选这些库**：`argon2-cffi` / `bcrypt`、`itsdangerous` 或 `PyJWT`、`pyotp` —— 全部成熟且可审计。

### 阶段 2 · 权限模型（3~5 天）

按文档 §4 的四层权限，落到本项目的**实际权限编码**：

```
# 生成与批次
batch.read              查看批次与图片
batch.create            创建新批次（消耗付费额度）
batch.delete            删除批次
batch.export            导出打包

# 效果图
effect.read             查看效果图
effect.generate         生成效果图
effect.background.manage 管理 AI 背景库
effect.params.manage    调整效果图参数

# 配置
settings.model.manage   管理模型与 API Key      ← 高危
settings.path.manage    修改输出路径            ← 高危
prompt.template.manage  修改提示词模板

# 系统
system.user.manage      用户管理
system.role.manage      角色管理
system.audit.read       查看审计
system.backup.manage    备份与恢复
```

| # | 项 | 要点 | 依据 |
|---|----|------|------|
| 2-1 | **唯一权限定义源** | 一份 `permissions.py`，前端导航、角色配置、接口校验、测试**都从它生成** | §4「唯一权限定义源」 |
| 2-2 | 服务端强制校验 | 每个接口加依赖注入校验；**不能只靠隐藏菜单** | §4 / §2.4 |
| 2-3 | 数据范围 | 本人 / 本组织 / 全部（取决于 Q1~Q3） | §4.3 |
| 2-4 | 字段权限 | 脱敏（如客户电话只显示后四位） | §4.4 |
| 2-5 | 越权防护 | 不信任前端传的角色/组织/归属；改 ID 也访问不到他人数据 | §4 |
| 2-6 | 角色模板 | 普通用户 / 设计师 / 组织管理员 / 审计员 / 超级管理员 | §5 |
| 2-7 | 交付权限矩阵 | 每个角色能访问哪些模块、执行哪些动作 | §5 |

### 阶段 3 · 数据隔离与审计（2~3 天）

| # | 项 | 要点 | 依据 |
|---|----|------|------|
| 3-1 | 批次归属 | 批次记录 `owner_user_id` / `org_id`；查询强制过滤 | §4 |
| 3-2 | 审计日志 | 独立 `audit.jsonl`：操作者稳定 ID、当时角色、组织、模块、动作、目标对象、请求 ID、结果、脱敏变更摘要 | §8 |
| 3-3 | 审计防篡改 | 只追加、普通管理员不可删改自己的记录 | §8 |
| 3-4 | 敏感操作审计 | API Key 变更、权限授予、批量导出**必须留痕** | §7.2 / §8 |
| 3-5 | 告警 | 暴力登录、连续越权拒绝、高权限授予、大量导出 | §8 |

## 四、⚠️ 必须说明的三个风险

| # | 风险 | 说明 |
|---|------|------|
| **R1** | **改造期间功能可能中断** | 加认证后，现有前端所有接口调用都要带上凭证 → 前端需同步改造 |
| **R2** | **现有批次数据的归属迁移不可逆** | Q4 定错后，重新分配会很麻烦 |
| **R3** | **付费额度按人生效需额外设计** | 多用户共用一个 API Key 时，用量归属与限额需要额外字段 |

## 五、我不建议做的事（附理由）

| 不建议 | 理由 |
|--------|------|
| 自研密码哈希 / 加密算法 | 文档 §2.3 明确禁止 |
| 用「隐藏菜单」当权限 | §2.4：所有权限必须服务端校验 |
| 多人共用管理员账号 | §2.11 / §3.14 |
| 一次性全量重构 | §2.12：要求渐进迁移 + 回滚方案 |
| 先开放 `0.0.0.0` 再补认证 | 这段时间等于无门禁，且 SSRF 立即可用 |
