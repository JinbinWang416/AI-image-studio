## 一、块 1：备份与异常恢复（最高优先级）

### 1.1 新增 `app/security/backup.py`

| 能力 | 设计 |
|------|------|
| 加密 | **AES-256-GCM**（`cryptography` 库，文档 §2.3 禁止自研算法） |
| 密钥来源 | ① 环境变量 `SHS_BACKUP_KEY`（base64 32 字节）<br>② 本机保护文件 `data/security/.backup_key`（首次自动生成，权限收紧） |
| 备份范围 | `data/security/*.json`、`logs/audit/`、`config/settings.json`、各 batch 的 `_manifest.json` |
| **不含** | `output/` 大图（体积原因，且属不可变产物） |
| 格式 | 单个 `.shsbak` 文件：`[magic][version][nonce][ciphertext][tag]` |
| 增量快照 | 写安全数据前自动触发；按内容 hash 去重，无变化则跳过 |
| 保留策略 | 默认保留最近 **10** 份，可配置；超出按时间清理 |

### 1.2 接口（权限 `system.backup.manage`）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/admin/backup/create` | 手动创建备份 |
| GET | `/api/admin/backup/list` | 列出备份（时间/大小/内容摘要，**不含密钥**） |
| POST | `/api/admin/backup/restore` | 恢复，**需二次确认**（请求体带 `confirm: "<备份ID>"`） |

**restore 的强制流程**：
1. 校验 `confirm` 与目标 ID 一致（防误操作）
2. **先自动创建"还原前备份"**（便于回滚）
3. 原子替换文件
4. **全程写审计**（`action=backup.restore`，含"还原前备份 ID"）
5. 返回明细：恢复了哪些文件、还原前备份的位置

### 1.3 紧急恢复通道 `tools/emergency_recover_admin.py`

**触发场景**：唯一管理员被锁/被删、`security.json` 损坏导致**无人能登录**。

| 能力 | 实现 |
|------|------|
| 修复损坏 JSON | 原子重建（从最近自动快照恢复；无快照则重建结构并保留可解析部分） |
| 重置首个 admin 密码 | 交互式输入新密码，走同一套强度校验 |
| 解除全部会话锁定 | 清空 `sessions.json` 的锁定与登录失败计数 |
| **仅限本机** | 校验：进程所在机器 == 数据所在机器；且检测是否通过远程会话调用 |
| **二次确认** | 必须输入 `RECOVER` 字样才执行 |
| 恢复日志 | 写入 `logs/emergency_recover_*.log`（含时间、动作、结果） |
| 干跑模式 | `--dry-run` 只报告将做什么，不修改 |

### 1.4 `JsonStore` 损坏自愈

**当前**：`load()` 捕获 `JSONDecodeError` → 返回默认值 → **账号静默消失**。

**改为**：
```
load()
 ├─ 正常 → 返回
 ├─ 文件不存在 → 返回默认值（首次启动，正常）
 └─ 解析失败（损坏）
      ├─ 尝试从最近自动快照恢复 → 成功则记 WARNING 日志 + 返回快照内容
      ├─ 无快照 → 把损坏文件重命名为 *.corrupt.<时间戳>（**保留证据**）
      │           + 记 ERROR 日志 + 返回默认值
      └─ 绝不静默丢弃
```

### 1.5 磁盘/IO 容错

| 场景 | 行为 |
|------|------|
| `OSError` / `ENOSPC` | 抛 `StorageFullError`（结构化） |
| 接口层 | 返回 `{"detail": "...", "code": "storage_full"}`，HTTP 507 |
| 日志 | 记录但不含路径细节 |
| 前端 | 明确提示「磁盘空间不足，请清理后重试」+ 重试按钮 |
| 栈追踪 | **绝不外泄** |

### 2.1 新增 `app/security/monitor.py`

数据源 = **审计日志**（已有，追加写）。

| 检测规则 | 阈值（可配置） | 告警级别 |

| 单位时间登录失败 | 5 分钟内 ≥ 8 次 | 中 |

## 三、块 3：CSRF 与 IP 级限流

### 3.1 CSRF 双提交 token

| 项 | 设计 |
|----|------|
| 下发 | 登录成功后 `Set-Cookie: shs_csrf=<随机>`（**非 HttpOnly**，前端可读） |
| 携带 | 写接口带 `X-CSRF-Token` 头 |
| 校验 | 中间件比对头与 cookie，不一致 → **403 + 审计** |
| 适用 | 所有 POST/PUT/PATCH/DELETE |
| 豁免 | 公开白名单（`/api/auth/login`、`/api/auth/status`、`/api/auth/setup`） |
| 兼容 | 无 cookie 的 CLI/脚本调用：若请求带有效 `Authorization: Bearer <session>` 则豁免 |

### 3.2 IP 级登录限流

| 项 | 设计 |
|----|------|
| 维度 | **IP + 账号** 双维度（账号级已有 `failed_attempts`） |
| 窗口 | 滑动窗口：同 IP 每分钟失败 ≥ 10 → 临时封禁 15 分钟 |
| 返回 | HTTP **429**，`code=rate_limited` |
| 审计 | `error_kind=rate_limited` |
| 存储 | 内存 + 落盘（重启不丢） |
| 与现有关系 | **并存不冲突**：`orchestrator.RateLimiter` 管图像 API 调用节流，本模块管登录 |

### 4.2 启动一致性自检（写入 server.py 启动钩子）

**校验三方一致**：
1. `permissions.py` 定义的权限码
2. `access_rules.py` 引用的权限码
3. `admin_routes.py` / `auth_routes.py` 里 `require_permission(...)` 用到的权限码
4. 各角色模板引用的权限码

**发现悬空/未登记 → 直接启动报错并列出差异**（对应原规划用例 13）。

> 这一步很关键：**防止"权限码写错但没人发现"导致接口实际无人可访问或人人可访问**。

## 八、风险与回滚

| # | 风险 | 缓解 | 回滚 |
|---|------|------|------|
| R1 | 加密密钥丢失 → 备份无法解密 | 密钥同时支持环境变量；首次生成时**明确提示用户备份密钥** | 备份文件可弃用，不影响运行数据 |
| R2 | JsonStore 自愈误判（把正常文件当损坏） | 只在 `JSONDecodeError` 时触发；恢复前先复制原文件 | 保留 `.corrupt.*` 原文 |
| R3 | CSRF 上线导致现有前端全部写请求失败 | 前后端**同批改动**；提供 `Authorization` 头豁免通道 | 中间件加开关 `SHS_CSRF_DISABLED=1` |
| R4 | IP 限流误封正常用户 | 阈值可配；封禁时长短（15 分钟）；管理后台可解封 | 清 `data/security/ratelimit.json` |
| R5 | 启动自检过严导致服务起不来 | 提供 `SHS_SKIP_SELFCHECK=1` 应急跳过 | 修正权限码即可 |
| R6 | `cryptography` 安装影响现有环境 | 先 dry-run 验证依赖可解析 | `pip uninstall cryptography` |

> **每一项改动都不触碰 `output/` 与历史批次**（AGENTS.md 硬约束）。
