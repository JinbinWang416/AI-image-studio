## 二、关键决策点（需要你确认）

### 🔴 D1：用 `dataclass` 还是 `pydantic`？

| 选项 | 优点 | 缺点 |
|------|------|------|
| **A. dataclass 子类**（推荐） | **零新依赖**；与项目现有风格一致（`Config` 就是 dataclass）；`dataclasses.replace()` 已在使用 | 校验要手写（但现在 `validate()` 也是手写） |
| **B. pydantic BaseSettings** | 自动校验、类型强制、环境变量集成 | **新增依赖**；`Config` 语义变化（不可变/校验异常）；现有 `dataclasses.replace` 调用要改 |

**我的建议：A** —— 项目是**单机本地工具**，`pydantic` 带来的收益（自动校验）不足以抵消依赖与行为变化的风险。

### 🔴 D2：旧字段访问要不要保留兼容？

现在 11 个文件用 `cfg.print_dpi` / `cfg.concurrency` 这种**平铺访问**。

| 选项 | 说明 |
|------|------|
| **A. 保留兼容属性**（推荐） | 新结构 `cfg.print.dpi`，同时用 `@property` 保留 `cfg.print_dpi` → **11 个文件一行都不用改**，风险最低 |
| **B. 全量改调用点** | 更"干净"，但要改 11 个文件 + 5 个测试，**风险高、收益低** |

**我的建议：A** —— 文档也说"不引入任何运行时行为变化，现有 import Config 的代码无需改调用方式（用兼容属性或提供适配器）"。

### 🟠 D3：本次做到哪个 Phase？

| 选项 | 内容 | 工作量 | 风险 |
|------|------|--------|------|
| **A. 只做 Phase 0**（拆 Config） | 收益最大、风险最低 | 约 3~4 h | 低 |
| **B. Phase 0 + Phase 1** | 再按边界重新分包 | 约 8~10 h | **中**（大量 import 路径变化） |
| **C. 0+1+2** | 再加统一 Job 执行器 | 约 14~18 h | **高**（改动编排核心） |
| **D. 全部 5 个 Phase** | 含进程池 + 前端工程化 | 数天 | 极高 |

**我的建议：先 A** —— 文档第 6 节也明说"优先做 Phase 0 和 Phase 1，这两步收益最大"。
**Phase 0 做完且测试全绿后，再单独决策 Phase 1**。理由是 Phase 1 会动**所有 import 路径**，一旦出问题排查成本远高于 Phase 0。

### 3.3 兼容层设计（关键 —— 实测后修正）

**先说结论：`@property` 只能解决"读字段"，解决不了 `dataclasses.replace`。**

#### 实测发现

**`dataclasses.replace` 有 12 处，全部在 `app/web/server.py`**：

```python
dataclasses.replace(cfg, output_root=LOCAL_PROFESSIONAL_ROOT, budget_limit=18)
dataclasses.replace(cfg, realism_iteration=next_realism)
dataclasses.replace(cfg, overwrite=True)
dataclasses.replace(cfg, base_url=safe_url)
dataclasses.replace(cfg, reference_assets=..., effect_background_asset=...)
```

**问题**：`replace()` 只认 **dataclass 的字段名**。拆成嵌套后 `output_root` 不再是字段 →
**这 12 处会直接抛 `TypeError: __init__() got an unexpected keyword argument`**。

#### 解决方案：`with_config()` 兼容工厂

```python
# app/core/config.py
_FLAT_TO_GROUP = {
    # 旧扁平字段名 → (子配置名, 子字段名)
    "output_root":        ("output", "root"),
    "budget_limit":       ("guard", "budget_limit"),
    "realism_iteration":  ("prompt", "realism_iteration"),
    "base_url":           ("provider", "base_url"),
    "overwrite":          ("output", "overwrite"),
    "reference_assets":   ("image_workflow", "reference_assets"),
    "effect_background_asset": ("effect", "background_asset"),
    "print_dpi":          ("print", "dpi"),
    # … 57 个字段全部映射
}

def with_config(cfg: Config, **overrides) -> Config:
    """按**旧扁平字段名**覆盖配置，自动路由到对应子配置。

    用法与 dataclasses.replace 完全一致，只是把名字换掉：
        with_config(cfg, output_root=X)   # 内部 → output=replace(output, root=X)
    """
```

**改动量**：
- **`server.py` 的 12 处**：`dataclasses.replace(` → `with_config(`（**机械替换，参数名不变**）
- **其余 10 个文件**：**零改动**（只读字段，靠 `@property` 兼容）

#### 测试里的 `Config(...)` 构造（5 处）

```python
# tests/test_account_recovery.py:104、test_batches.py:44、
# test_effect_outputs.py:66、test_openai_regeneration.py:67 …
Config(provider="mock", output_root=Path(...), ...)
```

**处理**：这些是**构造**（不是 replace），`@property` 帮不上。
**方案**：提供 `make_config(**flat_kwargs)` 工厂 → 5 处改成 `make_config(...)`，**参数名同样不变**。

**所以总改动量 = 12（replace）+ 5（构造）= 17 处机械替换**，且**参数名全部保持原样** —— 风险可控。
